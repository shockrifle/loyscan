# Test-driven development in LoyScan

Every change starts with a failing test, and the gate (root `CLAUDE.md`) passes before every commit
(lint, since #126: CI runs it, [[ci]]).
The rules and why: [[2026-10-12-tdd-and-coverage]]. This page is the how.

## The loop

1. **Pick the next acceptance criterion** of the issue. Criteria are phrased as testable statements; if one isn't,
   rephrase it first (in the issue).
2. **Red.** Write one test for it in the right place (table below) and run only that class:
   `./gradlew testDebugUnitTest --tests '*DetailViewModelTest'`. It must fail, and the failure must name the missing
   behaviour. A compile error means the API doesn't exist yet. Add the bare signature (returning a stub) so the
   test compiles and fails on its assertion.
3. **Green.** Write the least code that passes. Run the class again.
4. **Refactor** with the tests green: names, duplication, moving code to the right layer.
5. Repeat until the criteria are covered. Then run the whole suite and the gate (root `CLAUDE.md`). If coverage
   rose, raise `minBound` in `app/build.gradle.kts` to the new whole percent in the same commit
   ([[2026-10-09-coverage-gate-kover]]).
6. **Commit** with the wiki update. Say what the red step was in the message when it isn't obvious.

**Bug fix:** step 2 is a regression test that reproduces the bug through the public API. Run it and keep the
failure message for the commit, then fix it. Example: `12357a3` (#14). When the cause isn't known yet, the
`diagnosing-bugs` skill builds that failing test (or another loop that goes red) first ([[agent-skills]]).

Set `JAVA_HOME` first from a terminal (root `CLAUDE.md`).

## Seams: where a test looks

A test goes through a **seam**: the public interface where the behaviour is visible without reaching inside. That
means a ViewModel's `state`, a repository's interface, a DAO's queries, a screen's visible nodes and its recorded
`*Directions`, a domain function's return value. Private functions, a class's fields and a fake's internals are
not seams. The test should survive a rewrite of the code behind the seam.

Name the seam before writing the test: when planning an issue, each criterion maps to the test that proves it *and
the seam it goes through* ("a deleted card's photo files are gone → `RoomLoyaltyCardRepositoryTest`, through the
repository's `delete` and `FileCardPhotos.exists`"). If the only seam that can see the behaviour is too shallow
(the bug needs navigation, the seam is one ViewModel), use a deeper layer from the table below, not a hook into
the code.

Checking a side effect directly (the files on disk, a row in the database) is right when that effect *is* the
behaviour, like "no orphaned photo files". It is wrong when the interface could show it: read a repository write
back through the repository, not with SQL.

## Tests that can't fail

- **Tautological.** The expected value is computed the way the code computes it, so the test passes by
  construction: `assertThat(checkDigit(number)).isEqualTo(luhn(number))` with the same algorithm, or an expected
  string built with the same formatting call. Expected values come from an independent source: a literal worked
  out by hand, a vector from the specification or a published example, a made-up number that follows the store's
  rules ([[add-a-catalogue-store]]).
- **Implementation-coupled.** The test breaks when the code is refactored but the behaviour hasn't changed: it
  checks a private helper or the order of internal calls instead of the outcome. A call count on a fake is fine
  when the count is the behaviour: a delete reaches the repository exactly once (`DetailViewModelTest`,
  `deleteCalls`).
- **Never seen red.** A test that was never run against code without the behaviour proves nothing. Step 2 of the
  loop is why every test is seen failing first.

Robolectric means `@RunWith(AndroidJUnit4::class)`. Keep end-to-end tests few, one per user flow; behaviour
details belong in the per-layer tests.

## Naming and shape

- Class: `<ClassUnderTest>Test`. Method: `subject_condition_expectedResult` or `behaviour_inPlainWords`, e.g.
  `getByIdWithStore_unknownId_emitsNull`, `clickingACard_navigatesToItWithItsStoreColor`.
- One behaviour per test, arranged as arrange / act / assert with blank lines between them. Assertions use Truth
  (`assertThat`), and `Flow`s are tested with Turbine (`flow.test { awaitItem() … }`).
- A regression test is named after the behaviour; a `// #N` comment links the issue.

## Fixtures and doubles

Shared helpers are in `testing/`:
- **Fixture builders**, `aLoyaltyCard()`, `aStore()`, `aStoreEntity()`, `aLoyaltyCardEntity()`: every field has a
  default, so a test names only what it is about. Add a builder when you add a model. Use example data only,
  never real stores.
- **Fakes**, e.g. `FakeLoyaltyCardRepository` and `FakeStoreRepository` (each a `MutableStateFlow` you set): a fake implements the real
  interface *and its edge cases*. `FakeLoyaltyCardRepository(photos = …)` takes a `FakeCardPhotos`, and its `update` then deletes the
  photos an edit drops, as Room's does (`CardFormViewModelTest` wires it, #141). For example, `getByIdWithStore` emits `null` for a missing id, as Room does. A failure the code must
  survive is a switch on the fake: `FakeLoyaltyCardRepository.addFailure` makes `add` throw, and `loadGate` holds back `getAllWithStore` until it completes (`addGate`, `updateGate` and `deleteGate` hold a write the same way, on both repository fakes). To clear a ViewModel, as leaving its screen does, create it with `ViewModelStore().keep { … }` (`testing/ViewModelStores.kt`) and call `clear()` on the store (`CardFormViewModelTest`, #64). A ViewModel restored after its activity was destroyed is built from a **snapshot** of the handle (`SavedStateHandle(handle.keys().associateWith { handle.get<Any?>(it) })`), taken where the activity would save its state, not from the same handle: a write made after that point never reaches the restored ViewModel on a device, but would through a shared handle ([[2026-11-11-restored-form-saved-a-duplicate]], #99). For a form whose Save was tapped, that point is after `save()` returns and before the save ends, held by the fake's `addGate` / `updateGate` (`snapshotWhileTheSaveRuns`, #141). `FakeStoreRepository.setLogo` sets any store's logo (`setLogoFailure`, `setLogoGate`); the files are the photos fake's (#151).
  When you change an interface's contract, change the fake in the same commit. No mocking library.
- **`FakeCardPhotos`** stands in for `CardPhotos` in ViewModel and screen tests: `stored` is the set of photo names
  that exist. `stage` names staged files `staged-1`, `staged-2`… (listed in `staged`), `crop` names the framed photo
  `photo-1`, `photo-2`… (the pairs in `cropped`) and drops the staged one; `cropLogo` does the same for a store logo,
  named `logo-1`… (pairs in `croppedLogos`, #151); `stagePhoto` copies a stored photo to `staged-N` too (listed in
  `stagedPhotos`; a name not in `stored` throws); `importFailure` / `importGate` make either copy
  fail or hold, `cropFailure` makes the crop fail, `existsGate` holds `exists` (a file check in flight, #151). `newCapture` names captures `capture-1`… with a
  `content://photos.test/…` Uri, lists them in `captures` and adds them to `stored`. Because a pick stages then crops
  asynchronously, a crop-flow test asserts on `viewModel.state.value` after driving both steps (a `getStateFlow` reads
  back even before Turbine delivers the item), rather than on a Turbine item.
  It only answers `exists`: the image loader still looks for the file in `files/card_photos/`. A screen test that needs
  the photo to load writes one there with `File.writeOnePixelPng()` (`testing/PhotoFiles.kt`) and waits for it in the
  app loader's memory cache, idling the main looper (`ListScreenTest.aCardWithAFrontPhoto_…`); a name with no file
  there is a photo that fails to load (`aFrontPhotoThatCantBeLoaded_…`).
- **`Throwable.rootCause`** (`testing/Throwables.kt`): the innermost cause. A parser test that must tell a rule check
  from a JSON error asserts the root cause is exactly `IllegalArgumentException` (what `require` throws), while a
  JSON error's root is a `SerializationException`, a subclass
  (`CardNumberRulesTest.parse_rejectsInvalidRuleDefinitions`, #115). It was added for kotlinx-serialization 1.12,
  which wrapped the check's exception in a `JsonException`; 1.13 reverted that (PR #163), and the check holds for both.
- **`writeOnePixelPng()` / `writeWidePng()`** (`testing/PhotoFiles.kt`): a real 1×1 or 2×1 PNG written where the app's
  loader finds it; the wide one is a wordmark-shaped picture for the logo crop's zoom-out (#151).
- **`WAIT_TIMEOUT_MS`** (`testing/Waits.kt`, 10 s): the timeout every `waitUntil*` passes, in screen and app tests alike. `WaitTimeoutsTest` fails on one that doesn't (#59).
- **`MainDispatcherRule`** for anything that uses `viewModelScope`. A timer in a ViewModel takes its duration as a
  constructor parameter (`ScannerViewModel(hintDelay)`): `advanceTimeBy` tests it in virtual time, and a screen test
  passes `Duration.ZERO`. A timeout around work on another thread fires at once under `runTest`, which jumps virtual
  time ahead whenever the test thread is idle: run the work on the test scheduler behind a `CompletableDeferred`, or
  use `runBlocking` for a test about real threads (`ZxingCppPictureReaderTest`, #79).
- **`TemporaryPreferencesModule`** replaces `PreferencesModule` in every `@HiltAndroidTest`: a new preferences file per
  test, since DataStore throws when two stores open one file.
- **`FakePictureReaderModule`** replaces `PictureReaderModule` in every `@HiltAndroidTest`: one `FakePictureReader`
  that the test injects and sets.
- **`InMemoryDatabaseModule`** replaces `DatabaseModule` in every `@HiltAndroidTest`: an empty database that the
  test injects and fills.

Make code testable through constructor parameters, not test hooks. Pass a ViewModel and `*Directions` into
screens, and an `Executor` into callbacks. See [[architecture]] → Testing seams.

## Running and reading coverage

- `./gradlew testDebugUnitTest`: all tests. Report: `app/build/reports/tests/testDebugUnitTest/index.html`.
- `./gradlew koverVerify`: the coverage gate (it runs the tests too). `./gradlew check` runs it as well.
- `./gradlew lintDebug`: Android lint; an error fails it, and the gate and CI include it (#126).
- `./gradlew koverHtmlReportDebug`: line-by-line report at `app/build/reports/kover/htmlDebug/index.html`. Red
  lines are untested. Look at them before deciding a test is "done".
- More on the commands and the test libraries: [[build-and-run]] → Tests. CI runs the same gate on every PR, as a merge gate,
  and on `master`: [[ci]].
