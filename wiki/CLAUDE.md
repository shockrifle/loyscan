# LoyScan wiki — schema

This file is the single source of truth for **when** to update the wiki, **how** to write pages, and
**what** categories exist. Every session that touches LoyScan reads it and treats "When to update" as
a checklist for the task at hand. Pattern: Karpathy's LLM Wiki
(https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).

## Layers

1. **Sources — read-only ground truth.** Never edited during wiki maintenance.
   - The codebase: `app/` (single Gradle module `:app`), `gradle/libs.versions.toml`, root
     `build.gradle.kts` / `settings.gradle.kts`.
   - Room schema exports: `app/schemas/` (generated by KSP, committed).
   - Store catalogue: `app/src/main/assets/catalogue/stores.json` ([[store-catalogue]]).
   - Version control: `git log`, `git show <sha>`, `git blame`. Remote: GitHub
     `git@github.com:shockrifle/loyscan.git` (`origin`, added 2026-10-08). Work was committed directly to
     `master` until 2026-11-09 and lands through pull requests since ([[code-review]]). History before
     2026-10-08 has no issues or PRs, so the "why" for it must come from commit diffs, the code, or the
     person you're working with; for later work, also check PRs/issues with `gh`.
   - `wiki/assets/` — raw human-dropped material (notes, screenshots, transcripts). Read-only:
     compile it into pages, never edit the files themselves.
   - Prior Claude Code session transcripts under `~/.claude/projects/C--workspace-LoyScan/`.
2. **The wiki — writable, compiled artifact.** Everything under `wiki/` except `assets/`.
   Cross-linked Markdown using Obsidian-style `[[page-name]]` links (file name without `.md`).
   Page names must be unique across folders; the only exception is the per-folder `_index.md`, which
   is linked by path with an alias: `[[tech-debt/_index|tech-debt]]`.
3. **The schema — this file.**

## Layout

```
wiki/
├── CLAUDE.md           # this schema
├── index.md            # map of content — human-facing landing page
├── architecture.md     # layering + worked end-to-end example (template for new features)
├── glossary.md         # domain + codebase vocabulary
├── faq.md              # questions worth remembering
├── _log.md             # append-only changelog of wiki updates (newest first)
├── apps/               # one page per runtime surface (currently: the Android app)
├── features/           # one page per user-visible feature or flow
├── workflows/          # how things get done — build, run, change the DB schema, add deps
├── runbooks/           # what to do when something breaks — step-by-step, real commands
├── integrations/       # external systems we depend on (contract + quirks)
├── scripts/            # notable scripts / CLIs
├── decisions/          # YYYY-MM-DD-<slug>.md — one per decision
├── bugs/               # YYYY-MM-DD-<slug>.md — one postmortem per notable bug
├── tech-debt/          # one page per longer-lived owed work item
├── hacks/              # one page per short-lived workaround
└── assets/             # READ-ONLY raw sources (not wiki pages)
```

Every folder has an `_index.md` (purpose, page format, and for `decisions/`, `bugs/`, `tech-debt/`,
`hacks/` an Active/Open vs Resolved/Removed split — items **move** between sections, they are not
deleted).

## When to update the wiki (the maintenance contract)

Treat this as a checklist at the end of every non-trivial task:

- [ ] **New app / top-level surface** (e.g. a widget, Wear OS module, second Gradle module) →
      `apps/` (rare).
- [ ] **Non-trivial feature implemented or modified** → `features/<feature>.md`, with its entry points
      (path and symbol). Update [[architecture]] if the layering changed.
- [ ] **Architectural/design decision made** → `decisions/YYYY-MM-DD-<slug>.md`. Capture the *why*;
      skip if the why is obvious from the diff.
- [ ] **Workaround/hack added** → `hacks/<slug>.md`. **Longer-lived accepted debt** →
      `tech-debt/<slug>.md`. Add an entry to the folder `_index.md` either way.
- [ ] **Non-trivial bug fixed** → `bugs/YYYY-MM-DD-<slug>.md` — only when the root cause was
      surprising or the class of bug is likely to recur. Skip fixes the diff fully explains.
- [ ] **External integration touched/changed** (image hosts, future barcode/scanner libs, any
      network API) → `integrations/`.
- [ ] **Script / Gradle task / workflow added, renamed, removed** → `scripts/` or `workflows/`.
- [ ] **New kind of test, fixture or fake** → [[tdd]] (the per-layer table) and [[architecture]] → Testing seams.
- [ ] **Room schema / DB version changed** → update [[database-schema-changes]], and [[store-catalogue]] if the
      catalogue format changed.
- [ ] **Non-obvious question came up** → [[faq]]. **Domain term came up** → [[glossary]].
- [ ] **Incident handled / recurring failure found** → `runbooks/`.
- [ ] **Files dropped in `assets/`** → compile them into the right pages; note the source file name.
- [ ] **A tech-debt / hack item was paid down** → move it to the Resolved/Removed section of its
      `_index.md` and add a "Resolved" line with the commit SHA to the page; the commit closes its issue.
- [ ] **New tech-debt / hack page** → also open a GitHub issue (label `tech-debt` / `hack`) and put its
      link in the page's Status line.
- [ ] **Always** append one line to [[_log]].

## GitHub Issues vs this wiki

Work is tracked in GitHub Issues on `shockrifle/loyscan` (use `gh`). The split:

- **Issue = what and whether.** Scope, acceptance criteria, status, milestone. **Acceptance criteria are
  testable statements:** observable behaviour with its input and expected result ("tapping a card opens its
  detail", "an empty brand colour falls back to `surfaceVariant`"), not tasks ("refactor X") or vague qualities
  ("works well"). Each criterion maps to at least one test ([[tdd]]). Documentation criteria (a wiki page, a
  decision) are fine as they are. Labels: `feature`, `bug`,
  `tech-debt`, `hack`, `needs-field-check` (moves only with a real card or a till test). Milestones:
  `v1 – core cards` (closed), `v1 – extras`, `v1 – release`, `Later`.
- **Wiki = why and how.** Decisions, architecture, feature docs, postmortems, runbooks. Wiki pages don't hold
  backlogs or TODO lists; issues don't hold design rationale (link to the wiki page instead).
- **Linking.** Commits and the PR reference the issue (`Fixes #N` closes it when the PR merges into `master`). Wiki pages that
  correspond to an issue (tech-debt, hacks, features in progress) link it; issues link the wiki page with a full
  `https://github.com/shockrifle/loyscan/blob/master/wiki/...` URL.
- **Public-safe.** The repo is public ([[2026-11-23-public-repository]]): no local absolute paths, personal data,
  credentials, or third-party proprietary material in issues, commits or wiki pages. `PublicSafeRepoTest` checks the
  tracked files; the rest is swept by hand ([[public-safe-sweep]]).

## When NOT to update

- Trivial changes: renames, formatting, lint fixes, dependency bumps with no behavior change.
- Anything already in the root `CLAUDE.md` — link to it, don't duplicate.
- Anything trivially derivable from reading the code (a list of DAO methods, a list of composables).
- Speculative future plans. The wiki describes what **is**. (Visible TODOs in code may be recorded as
  tech debt, phrased as "X is not implemented", not "we will build X".)
- Areas the current task didn't touch.

When in doubt, prefer linking to the source (path and symbol, commit SHA) over copying it. **When in doubt
whether something is wiki-worthy, don't write it** — a smaller true wiki beats a padded one.

## How to write pages

- **One concept per page.** Split when a page passes ~200 lines.
- **Lead with the answer**, then provenance and detail.
- **Cross-reference liberally** with `[[page-name]]`. Every link must resolve to an existing page.
- **Provenance is mandatory for non-obvious claims**: the repo-relative path and the symbol (`AppDatabase.VERSION` in
  `app/src/main/java/com/bdaniel/loyscan/data/local/db/AppDatabase.kt`), and commit SHAs (short, 7 chars). **No line
  numbers**: they went stale with every edit above them, even in files that rarely change, and nothing checked them
  (#222). For code as it was, give the SHA ("as of `45a33e1`") and the current name ("now `getByIdWithStore`").
  `WikiReferencesTest` fails on a line number, on a repo path that isn't tracked and on a test method no test
  declares. Mark inferences explicitly: *"(inferred from diff; not stated in commit)"*. Commit messages in this
  repo are terse, so most "why"s are inferences — say so.
- **Contradictions**: if a page disagrees with the code or with another page, keep the truer version,
  note the correction on the page, and record it in [[_log]]. Don't silently overwrite.
- **Dates are absolute** `YYYY-MM-DD`. Never "recently" / "last week".
- Paths are repo-relative. `<pkg>` is **not** used as an abbreviation — write full paths so they are
  clickable.
- Frontmatter is not required. Start with `# Title` then a one-paragraph summary.

### Page skeleton — `decisions/YYYY-MM-DD-<slug>.md`

```markdown
# <Decision title>

**Status:** Active | Superseded by [[...]] · **Date:** YYYY-MM-DD · **Commits:** abc1234

## Context
## Options considered
## Decision
## Why            <- load-bearing; if unknown, say "Not recorded" and give the best inference, labelled
## Consequences
```

### Page skeleton — `bugs/YYYY-MM-DD-<slug>.md`

```markdown
# <Bug title>

**Fixed in:** abc1234 · **Date:** YYYY-MM-DD · **Area:** [[feature-page]]

## Symptom
## Root cause
## Fix
## Lessons        <- what to do differently / what pattern to watch for
```

### Page skeleton — `tech-debt/<slug>.md` and `hacks/<slug>.md`

```markdown
# <Title>

**Status:** Open | Resolved (sha) · **Since:** YYYY-MM-DD (sha) · **Where:** path + symbol

## What
## Why it exists
## Risk / impact
## How to pay it down
```

### `_log.md` format

Append-only, **newest first**, one self-contained line per entry:

```
- YYYY-MM-DD · <action> · <pages touched> · <trigger: commit sha / task description>
```

Never rewrite past entries. Keep each entry on a single line (the file uses a union merge driver).

## Evolving the schema

The taxonomy is a starting point. When content genuinely fits no existing category:

1. create the folder + `_index.md`,
2. add it to the Layout tree above,
3. add a "When to update" trigger,
4. link it from [[index]],
5. log it in [[_log]].

Default to **not** adding a category when an existing one can absorb the content. Evolution should be
explicit and rare.

## Tooling boundaries

- No code formatter or Markdown linter is configured in this repo (no ktlint/Spotless/Prettier/
  `.editorconfig`, checked 2026-10-08). If one is added, exclude `wiki/` from it in the same commit.
- `wiki/` is outside every Gradle source set; it is never part of the build.
- Android Studio "Reformat Code" on a Markdown file can rewrap it — don't run it on wiki pages.
- The wiki is committed to git. **Wiki updates land in the same commit as the code change that
  triggered them**, so `git log` ties them together.
- `wiki/_log.md` has `merge=union` in the root `.gitattributes` so concurrent appends don't conflict.
