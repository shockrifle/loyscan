# Coverage gate with Kover, ratcheted upwards

**Status:** Active · **Date:** 2026-10-09 · **Issue:** [#27](https://github.com/shockrifle/loyscan/issues/27)

Line coverage of the JVM tests is measured by the Kover Gradle plugin. `koverVerify` fails the build below a
minimum. The minimum starts at the measured baseline and is only ever raised.

## Context
The project is moving to test-first work (#13). Without a number, untested code goes in unnoticed.

## Options considered
- **Kover** (JetBrains): built for Kotlin. Understands inline functions and Kotlin-generated code, and creates
  tasks per Android variant.
- **JaCoCo through AGP** (`enableUnitTestCoverage`): needs a hand-written report task to merge results and filter
  classes, and it reports Kotlin-generated bytecode as missed lines.
- **No gate, report only**: a report nobody reads doesn't stop coverage from dropping.

## Decision
- Plugin and configuration: the `kover { }` block at the end of `app/build.gradle.kts`.
- Commands:
  - `./gradlew koverHtmlReportDebug` and `koverXmlReportDebug` produce the reports.
  - `./gradlew koverVerifyDebug` checks the minimum. Plain `./gradlew check` runs it too, through the total
    `koverVerify`.
- **Excluded**, because there is no logic to test or it is generated code:
  - `com.bdaniel.loyscan.ui.theme` and its sub-packages, which includes the icon vectors in `Icons.kt`.
  - The `com.bdaniel.loyscan.widget.glance` package: Glance/AppWidget glue that runs only on a real home screen
    (the `provideGlance` wiring, the system receiver, and the refresher's `updateAll`/`getGlanceIds`). The logic it
    drives is tested — `toWidgetTiles`, `CardWidgetContent` and `CardWidgetUpdater` in `com.bdaniel.loyscan.widget`
    ([[card-widget]], #11, 2026-11-04). A `packages(…)` exclude, because Kover's class-name patterns proved
    unreliable for these classes while the package filter is exact.
  - Functions annotated `@Preview`.
  - Hilt/Dagger output: `*_Factory`, `*Module_*Factory`, `*.Hilt_*`, `*_MembersInjector`, `*_HiltModules*`,
    component classes.
  - Room `*_Impl`.
  - kotlinx.serialization `$$serializer`.
  - `BuildConfig`.
  - Kover patterns match **fully-qualified** names, which is why the Hilt pattern is `*.Hilt_*`, not `Hilt_*`.
- **The rule:** one line-coverage `minBound`, currently **90 %**. History:
  - 63 % at the start (2026-10-09): 273 of 432 lines. The domain code was close to 100 %; the screens, mapper,
    repository and DI modules were mostly untested.
  - 90 % after the safety-net backfill (#30): 390 of 432 lines. Still uncovered: the DI module bodies,
    `hiltImageLoader` and the unused `BrandRepository`.
- **Targets:** about 80 % overall, and at least 90 % for `domain/`, `data/` and the ViewModels.
- Only the debug variant has unit tests. Release unit tests are turned off in `androidComponents { }`, because the
  Compose UI tests need `ui-test-manifest`, which is a debug-only dependency.

## Why
- **The ratchet:** whenever a change raises coverage, set `minBound` to the new measured value, rounded down to a
  whole percent, in the same commit. **Never lower it.** If a change cannot meet the bound, add tests; don't
  move the bar. The bar only goes up, so coverage can't slide back.
- **Starting point:** starting at the targets would fail every build until the backfill (#30) is done. Starting at
  the baseline means the gate is useful today.
- **Exclusions:** excluded code can't hide untested logic, and leaving generated code in would make the percentage
  mean less.

## Consequences
- The gate leaves about one line of headroom: 273/432 = 63.19 % against 63 % at the start, and 390/432 =
  90.28 % against 90 % after #30. So every new line of logic needs a test from the first feature commit on.
  That is intended: write the test first.
- **Per-package targets are not enforced yet.** Only the overall bound is checked. Add a rule with
  `filters { includes { packages(…) } }` per package once that package reaches its target.
- **Generated Room DAOs are excluded.** DAO behaviour is still tested, just through `Room.inMemoryDatabaseBuilder`
  (see [[build-and-run]] → Tests); it doesn't count towards the percentage.
